# REINT CHALLENGE

## Problem Statement

A UK-based energy utility client provides electricity to its customers via renewable energy sources such as wind generators and covers any additional energy needs through buying it via the day-ahead market.

The electricity generated by renewable wind energy is dependent on weather conditions. To estimate the quantity of electricity they would need to buy from the day-ahead market, they rely on weather predictions and make their decision on the amount on the previous day.

To aid their decision-making, I am implementing a web-based product that:
- helps the client understand and analyse the latest wind generation forecasts available at decision time, using the [WINDFOR](https://bmrs.elexon.co.uk/api-documentation/endpoint/datasets/WINDFOR/stream) dataset
- evaluates the accuracy of those forecasts quantitatively against actual wind generation from the [FUELHH](https://bmrs.elexon.co.uk/api-documentation/endpoint/datasets/FUELHH/stream) dataset (`fuelType = WIND`)

so that the team can make decisions on buying energy from the day-ahead market, while considering quantified error.

This tool is not meant to prompt the amount of energy that the team would need to buy on a particular day **directly**, but instead helps them make informed decisions based on generation forecast data analysis.

## Product Description

The tech stack used is Python (FastAPI), React (Vite) and Docker.

**Scope:** national-level wind generation (actuals and forecasts) from Elexon only, for purchase decisions made in January 2026.

### Key design decisions

- **Docker:** used so the app builds and runs identically on any machine (`docker compose up`) and to support container-based deployment. Note that Vercel does not run containers, so the deployment target determines whether Docker is used in production or only for local/review runs.
- **Latest available forecast:** for each target time, the forecast with the latest `publishTime` at or before the day-ahead decision cutoff on the previous day (D-1) is used. The default cutoff is assumed to be 12:00 UTC on D-1, and it can be changed per request through the `cutoff` parameter of the API endpoints in `main.py`.
- **Time handling:** all timestamps are handled in UTC internally (Elexon timestamps are UTC; the UK is on GMT in January, same as UTC so there is no offset in scope).
- **Error metrics:** MAE, RMSE and bias (mean error), with breakdowns such as by time of day and forecast horizon.
- **As-of methodology:** error margins for a delivery day use only periods already observed at the decision time, so no future information leaks in (see [Methodology](#methodology)).

## Methodology

### Decision-time forecast
Forecasts and their error ranges are calculated at half-hourly resolution. For each target half-hour, the forecast used is the latest WINDFOR publication with `publishTime` at or before the decision cutoff on the previous day (D-1). The default cutoff is 12:00 UTC and can be changed per request (`cutoff=HH:MM`).

For readability, the day-ahead forecast report/API returns hourly samples from the half-hourly forecasts and ranges rather than displaying every point. This is a presentation choice; the underlying forecasts, historical error calculations, and ranges remain half-hourly.

### As-of error statistics
Error margins shown for a delivery day are built **only from periods already observed at the decision time**, so nothing from the delivery day or later is used (no look-ahead).

- A past half-hour counts only once it has finished by the cutoff.
- **Window:** expanding (all history since 1 Jan, the default) or rolling (`window_days=N`, the last N days).
- **Minimum history:** 3 distinct days. Below that, the API returns `insufficient_history` and no range is shown.
- **Sign convention:** `error = forecast − actual` (MW). Positive means the forecast over-predicted wind, so a buyer relying on it would under-buy.

Metrics reported: MAE, RMSE, bias (mean error), MAE as a % of mean actual, share and average size of over- and under-forecasts, and error percentiles (5th, 25th, 50th, 75th, 95th). Breakdowns are by time of day, forecast horizon (`publishTime` to `startTime`), actual wind level (terciles) and delivery day.

### Plausible range for a delivery day
Because `error = forecast − actual`, `actual = forecast − error`. The range for each half-hour is therefore:

- lower = forecast − 95th percentile of past errors (floored at 0)
- upper = forecast − 5th percentile of past errors

The percentiles default to 5 and 95 (a nominal 90% range) and are configurable (`lower_pct`, `upper_pct`). The same pooled error distribution is applied to every half-hour of the day.

This range describes how far past forecasts were from actuals. It is information for the decision, not a recommended purchase quantity.

### Backtest
For every delivery day with enough history, the range is built using only information available at that day's decision time, then compared with actual generation. Backtest coverage is evaluated over the hourly report periods returned by the API and should be close to the nominal 90%.

Result on January 2026 data (12:00 UTC cutoff, P5–P95 range): **84.8%** of evaluated actuals fell inside the range.

## Limitations

- One pooled error distribution is applied to all half-hours. Errors differ by time of day and horizon (see the breakdowns), so the range is a simplification.
- The 12:00 UTC cutoff is an assumption, not a verified gate closure time.
- Past error is a guide to future error, not a guarantee.

## API

Interactive docs are at `/docs` when the backend is running. All times are UTC.

| Endpoint | Purpose | Main parameters |
|---|---|---|
| `GET /health` | Health check | none |
| `GET /api/meta` | Selectable delivery dates, cutoff in use, data-gap counts | `cutoff` |
| `GET /api/forecast/{forecast_date}` | Hourly report samples from the half-hourly forecasts and ranges, plus publish time, horizon, actual (if known), and as-of stats | `cutoff`, `window_days`, `min_days`, `lower_pct`, `upper_pct` |
| `GET /api/metrics` | Accuracy metrics and breakdowns over the whole period or a range | `cutoff`, `start`, `end` |
| `GET /api/backtest` | Share of actuals inside the as-of range, per day and overall | `cutoff`, `window_days`, `min_days`, `lower_pct`, `upper_pct` |

### Example Usage

Interactive API documentation is available at [http://localhost:8000/docs](http://localhost:8000/docs) when running locally. Replace `localhost:8000` with the backend address if needed.

Example request:

```text
GET http://localhost:8000/api/forecast/2026-01-02?cutoff=12:00&window_days=1&min_days=1&lower_pct=5&upper_pct=95
```

This example uses `window_days=1` and `min_days=1` to show a range with a short history window. The normal minimum is 3 distinct history days.

## Running locally

With Docker:

```bash
docker compose up --build
```

- Frontend: http://localhost:3000
- Backend API docs: http://localhost:8000/docs

Without Docker, start the backend and frontend in separate terminals from the repository root.

### Unix / macOS

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python -m app.forecast_data
uvicorn app.main:app --reload
```

In a second terminal:

```bash
cd frontend
npm install
npm run dev
```

### Windows PowerShell

```powershell
cd backend
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m app.forecast_data
uvicorn app.main:app --reload
```

In a second PowerShell terminal:

```powershell
cd frontend
npm install
npm run dev
```

The first run of `python -m app.forecast_data` fetches Elexon data and caches it under `backend/data/`. Subsequent runs use the cache unless it is refreshed.

## Deployment

The frontend and FastAPI backend deploy together as one Vercel project. The frontend calls the API on the same domain.

For an existing Vercel project:

1. Set **Root Directory** to the repository root (not `frontend`). This is required for Vercel to discover the root FastAPI entrypoint and Python dependencies.
2. Set **Framework Preset** to **FastAPI**.
3. Leave the dashboard **Build Command**, **Install Command**, and **Output Directory** blank. Do not override FastAPI's build: Vercel runs the frontend build from [`pyproject.toml`](./pyproject.toml), and `app.frontend()` serves the generated files while keeping API routes available. CDN promotion is disabled so FastAPI serves frontend assets directly rather than relying on Vercel's static-file collection.
4. Remove any `VITE_API_URL` value that points to `localhost`. Production builds use the same-origin FastAPI endpoints by default. Keep `VITE_API_URL` unset unless you are intentionally using a separately hosted API.
5. Redeploy the project.

The deployment uses the root [`app.py`](./app.py) entrypoint, installs runtime dependencies from [`pyproject.toml`](./pyproject.toml), builds the Vite app through the FastAPI build hook, and serves the API and frontend on the same deployment. The root [`requirements.txt`](./requirements.txt) mirrors those runtime dependencies for tools that use pip. In the build log, expect to see the frontend `npm ci` and `vite build` commands run; if Vercel finishes in milliseconds without them, it did not use this repository root/configuration.

For local development, continue running FastAPI and Vite separately as described above.
